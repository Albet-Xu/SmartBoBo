# paper-experience：论文写作经验记忆库（RAG）

本技能与 `paper-memory` MCP server 配套。模型通过 `mcp__paper-memory-<模式键>__paper_experience_*`
读写经验库；本技能说明**何时**查、**何时**存、怎么组织内容，以及红线约束。

> **库只有一个，实例有四个**：四个论文模式各挂一个实例名
> （`paper-memory-empirical` / `-modeling` / `-experiment` / `-review`），但**指向同一个集合
> `paper_experience` 与同一份本地数据目录**。这是有意设计——库分裂会让你"在这个领域积累的经验"
> 在另一个模式里检索不到。实证模式**额外**挂 `reverse-memory`（数据源采集经验见下）。

## 记忆库工具（模型可见名，前缀随模式变化）

- `paper_experience_search` —— 混合检索历史论文经验（scope 加权 + 方法标签过滤 + 语义向量）
- `paper_experience_get` —— 按 id 取单条完整详情（search 只回摘要，需要明细时用）
- `paper_experience_save` —— 沉淀一条经验（**置信度严格大于 2.0 才入库**；`applicable_when` 必填）
- `paper_experience_feedback` —— 采纳反馈：成功 +0.5 / 失败 −0.5
- `paper_experience_stats` —— 库统计 / Qdrant 状态 / 种子与真实沉淀条数
- `paper_experience_cleanup` —— 冷归档未复用旧经验（默认 dry-run）
- `paper_experience_sync` —— 把本地未同步经验重新推送到当前 Qdrant

`search` 返回的 `mode` 有三种含义，**看到 `local` 要主动告诉用户覆盖面变小了**：

| mode | 含义 |
| --- | --- |
| `vector` | 语义检索，正常 |
| `filter` | 只按标签/阶段过滤（没给检索词），从 Qdrant 拉全量候选 |
| `local` | **Qdrant 不可达，已降级为本地检索——覆盖面明显小于向量检索**（论文经验比逆向更依赖语义层） |

## 何时查（三个检索点）

**只在"检索能改变决策"的位置查**；检索不改变决策的地方只自省、不查（否则是白烧上下文）。

1. **S0/S1 定盘后、写 `design.md` 前** —— 查**方法经验**。能改变识别策略、事前分析计划、
   局限预期；不查就可能重蹈覆辙。
2. **S2 动手采集 / 参数标定前** —— 查**数据源经验**。实证模式这类经验在 `reverse-memory`
   里（"某数据源怎么拿"与"某站点怎么抓"是同一件事），用 `reverse_memory_search`。
3. **S5 评审返修后** —— 查**评审常打回点**。这是最能提升成稿质量的一步。

**S4 写作阶段不要查。** 写作阶段检索经验会诱导"经验进正文"（见红线）。

检索建议：传 `scope`（领域/主题键，如 `corporate-finance/policy-evaluation`）+
`method_tags`（方法标签）+ 已观察到的特征文本。`scope` 只做**排序加权**、不做硬过滤
（领域词典必然爆炸），真正的召回主力是 `method_tags` 与语义向量。

## 何时存（S5 出口 / S6 交付前，收尾必做）

1. **S5 评审返修后**沉淀经验（`review.json` 的 high 严重度问题是最有价值的原料）；
2. **S6 交付前**收尾沉淀（含阶段耗时与预算实耗这类 `process` 经验）；
3. 成功/失败/部分成功**都要沉淀**——失败经验（"这个方向试了 N 次都不行"）价值最高；
4. 记录参考过哪条历史经验（`used_experience_ids`），并在采纳后调 `feedback` 打分。

### 置信度锚点（按「项目复现数」，不按跑通次数）

| 置信度 | 语义 |
| --- | --- |
| 2.0 | 本次项目里试了一次、成功 —— **会被丢弃** |
| 2.5 | 本次项目里反复验证，或有两个独立证据点（两行 `results.tsv` / 两个数据集 / 两个模型设定） |
| 3.0 | 与**方法论文献**一致（能指向 methodology paper，不是自己的单个观察） |
| 3.5–5 | **跨项目复现过**：在 ≥2 个不同论文项目里都成立 |

**只有严格大于 2.0 才入库**，≤ 2.0 会被服务端直接丢弃（不留文件、不进库）。
**如实自评**——为了"消掉提醒"而虚报置信度，是把库做烂的最快方式。

同指纹（`scope + method_tags + kind + stage` 相同）再次入库走**强化**而非替换：
lessons 取并集、`confidence = min(5.0, max(旧,新) + 0.5)`、`confirmed_projects` 累加。
所以**换一个论文项目又验证一次同一件事，就如实再存一次**——这让"跨项目稳定"变成可累积的
机械事实，而不是靠自评。

## 红线（不可逾越）

| # | 红线 | 说明 |
| --- | --- | --- |
| 1 | **迁移判据：换一个数据集、换一个课题之后还成立吗？** | 不成立就**不沉淀**。这是决定库质量的第一道闸——"本项目的 dataset_v1 有 3842 行"毫无迁移价值，收了就是噪音。**候选草稿里的大部分条目本来就该被毙掉**，这是设计意图。 |
| 2 | **不沉淀具体研究结论与数值** | 只沉淀方法与坑。字段命名刻意避开 `finding` / `result_value` / `effect_size`，防"经验库变成二手数据源"。 |
| 3 | **不沉淀用户私有数据** | 数据集字段值、企业名、受访者信息一律不写。 |
| 4 | **负向经验必须带 `applicable_when`** | 否则不许入库（服务端会拒）。防"IV 在这个领域不好用"这类局部假象被泛化成迷信。 |
| 5 | **经验不得进正文、不得当引用** | 经验 id 只允许出现在 `design.md` 与 `cleaning-log.md` 的「参考经验」字段，**不允许出现在 `04-稿件/*`**。经验只能改变流程与检查表，不能改变结论。 |
| 6 | **不沉淀「如何规避查重 / 规避 AI 检测」** | 与本项目"引用真实可核验、数据真实可追溯、AI 参与如实声明"的立场一致。 |

**红线①与"仅供启发"的关系**：检索到的经验一律当作**待验证假设**，必须结合当前课题实测确认，
**禁止直接照搬**（换一个课题它可能不成立）。

## 与文献层的分工（最容易被混淆的一条）

| | 来源 | 可引用 | 去向 |
| --- | --- | --- | --- |
| **文献层** | 外部已发表文献 | ✅ 可引用 | `evidence.jsonl`（`type: literature`） |
| **经验层** | 自己上次项目 | ❌ **不可引用** | `design.md` 的「参考经验」字段 |

像"组数 <30 时聚类标准误下偏"这类**方法论事实**，应该走**文献层**（找到方法论原文 → 进证据层），
**不走经验层**。经验层存的是"我上次踩到了这个坑"，不是"这个事实为真"。

## 评审者不许读经验库

S5 的零上下文盲审要**明确告诉审稿人不要读经验库**——查经验库等于把执行者的先验注进审稿人，
那就变成"自己给自己出题"，盲审的成立条件被破坏。**经验只影响执行者的流程与检查表。**

## 方法标签速查（method_tags 建议值）

> 标签由**类型包**提供词表（见各 `paper-*` 类型包技能）。以下是常用值，可直接取用。

- **实证 / 计量**：`变量操作化` `口径一致性` `缩尾` `缺失机制` `样本框` `面板平衡`
  `DiD` `交错处理` `负权重` `IV` `弱工具` `RDD` `断点操纵` `PSM` `合成控制`
  `聚类层级` `安慰剂检验` `平行趋势`
- **建模**：`假设现实性` `可放松性` `存在性` `唯一性` `单调性` `比较静态` `量纲`
  `边界情形` `退化情形`
- **实验 / 仿真**：`多种子` `均值±标准差` `显著性检验` `独立test set` `预算对齐`
  `消融` `数据泄漏` `评测实现差异` `FDR` `参数扫描` `敏感性分析` `收敛判据` `随机种子`
- **综述 / 质性**：`PRISMA` `PICO` `检索式` `纳入排除` `去重` `灰色文献` `发表偏倚`
  `异质性` `编码本` `初始编码` `聚焦编码` `饱和度` `编码者间一致性` `匿名化`
- **案例研究**：`案例选择标准` `分析单位` `纵向数据` `三角验证`
- **流程 / 工具**：`数字漂移` `引用真实性` `可复现性` `阶段闸门` `空转返修` `图表规范`

`kind` 取值：`method`（方法与论证） / `data`（数据源与清洗） / `tooling`（工具与流程坑）
/ `review`（评审与返修） / `process`（流程与预算）。
`stage` 取值：`S0`–`S6`（六阶段骨架见 `paper-common` 公共段）。

## 内容组织

按照同目录 `log_template.md` 组织；`save` 时逐字段传入，memory_store 会按同样结构
生成可读 MD 日志并向量化入库。

## 半自动沉淀（S5/S6 的推荐流程）

不要靠回忆写经验——论文流程里已经有了**结构化落盘的经验原料**，用脚本机械提取，你只负责判断。

```bash
# 1) 从项目产物生成候选草稿（脚本只读，只回摘要，不会把 run.log 塞进上下文）
python <BoBo根>/scripts/paper_experience_candidates.py <论文项目目录>
#    → 产出 <论文项目目录>/05-评审/experience-candidates.md
#    想先看精简清单：加 --summary；想打印到屏幕：加 --stdout
```

提取来源与对应 `kind`：

| 来源 | 提取出什么 | kind |
| --- | --- | --- |
| `05-评审/review.json` 的 **high 严重度** issues | 这类论文的常见硬伤 | `review` |
| `05-评审/revision-log.md` 的「不改」条目 | 约束型经验（该退让为局限的地方） | `data` / `review` |
| `02-数据/cleaning-log.md` 的决策行 | 数据获取与清洗的坑 + 事前规则 | `data` |
| `03-实验/results.tsv` 的 `crash` / `discard` 行 | 「这个方向试了 N 次都不行」（**极有价值**） | `method` |
| `00-选题/progress.md` + token 台账 | 阶段耗时与预算实耗 | `process` |

**然后你逐条做四件事**：

1. **过迁移判据**——换一个数据集、换一个课题之后还成立吗？**不成立就毙掉**。
   脚本已做**预检**并把疑似项目特定的条目标成 `⚠️`（如带具体变量名、年份、样本量）；
   **草稿里大部分条目本来就该被毙掉，这是设计意图，不是草稿质量差**。
2. 给留下的条目补 **`applicable_when`**（必填，服务端拒收空值）。
3. 归一化 `scope` 为两级 `领域/子领域`；`method_tags` 优先取**类型包**里的词表值。
4. 如实自评 `confidence`，调 `paper_experience_save` 入库——**带上 `paper_project` 与 `artifacts`**，
   这样换项目复现时 `confirmed_projects` 才能机械累加。

> 脚本**不会**替你入库：是否入库、置信度多少、适用条件怎么写，全部由你判断。
> 这份草稿文件由脚本生成，**不要手写它**（改完产物重跑脚本即可覆盖）。
