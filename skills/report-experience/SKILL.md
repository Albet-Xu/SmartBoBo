# report-experience：文献汇报 PPT 经验记忆库（RAG）

本技能与 `report-memory` MCP server 配套。模型通过
`mcp__report-memory__report_experience_*` 读写经验库；本技能说明**何时**查、**何时**存、
怎么组织内容，以及红线约束。

> **与论文写作经验库是两套独立集合**：`report-experience` 存的是「怎么把论文讲成一场汇报」，
> `paper-experience` 存的是「怎么做研究、怎么写论文」。**不要互相写入**，
> 也不要指望在汇报库里查到计量方法经验。
>
> **本池的因果链是「制作动作 → 评分后果」**。所以经验里最有价值的一条是
> 「我做了 X，评分因此掉了 N 分」——而不是「我觉得 X 更好」。

## 记忆库工具（模型可见名）

- `report_experience_search` —— 混合检索历史汇报经验（**类型硬过滤** + 标签 + 语义向量）
- `report_experience_get` —— 按 id 取单条完整详情（search 只回摘要，需要明细时用）
- `report_experience_save` —— 沉淀一条经验（**置信度严格大于 2.0 才入库**；`applicable_when` 必填）
- `report_experience_feedback` —— 采纳反馈：成功 +0.5 / 失败 −0.5
- `report_experience_stats` —— 库统计 / Qdrant 状态 / 种子与真实沉淀条数
- `report_experience_cleanup` —— 冷归档未复用旧经验（默认 dry-run）
- `report_experience_sync` —— 把本地未同步经验重新推送到当前 Qdrant

`search` 返回的 `mode` 有三种含义，**看到 `local` 要主动告诉用户覆盖面变小了**：

| mode | 含义 |
| --- | --- |
| `vector` | 语义检索，正常 |
| `filter` | 只按类型/标签/阶段过滤（没给检索词），从 Qdrant 拉全量候选 |
| `local` | **Qdrant 不可达，已降级为本地检索——覆盖面明显小于向量检索** |

## 何时查（三个检索点）

**只在"检索能改变决策"的位置查**；检索不改变决策的地方只自省、不查（否则是白烧上下文）。

1. **R0 定盘后、写 `00-选题/brief.md` 前** —— 查**叙事骨架经验**。能改变页数取舍、
   章节划分与"哪些内容根本不讲"的决策；不查就可能重蹈覆辙。
2. **R3 页策划前** —— 查**版式与视觉经验**。PPT 的头号事故是文字溢出与图表错配，
   这类坑最适合用经验提前规避（`kind=visual`）。
3. **R5 评分返修后** —— 查**常见扣分点**（`kind=review`）。这是最能提升得分的一步。

**R4 生成阶段不要查。** 生成阶段检索经验会诱导"经验进页面正文"（见红线）。

检索建议：**一定要传对 `report_type`**（`single` / `multi` / `seminar` / `proposal` / `survey`）——
它是硬过滤，组会汇报与开题汇报踩的坑几乎不通用。再传 `tags`（现象标签，如 `文字溢出`、
`图表错配`、`对比矩阵`）与特征文本（如「15 页 / 中文 / 2 篇实证论文」）。

## 何时存（R5 出口 / R6 交付前，收尾必做）

1. **R5 每轮评分返修后**沉淀——`04-评审/score.json` 的**逐页扣分项**是最有价值的原料；
2. **R6 交付前**收尾沉淀（含阶段耗时与轮数这类 `process` 经验）；
3. 成功/失败/部分成功**都要沉淀**——失败经验（"这个叙事结构连改两轮都上不去分"）价值最高；
4. 记录参考过哪条历史经验（`used_experience_ids`），并在采纳后调 `feedback` 打分。

### 置信度锚点（按「跨汇报复现数」，不按跑通次数）

| 置信度 | 语义 |
| --- | --- |
| 2.0 | 本次汇报里试了一次、成功 —— **会被丢弃** |
| 2.5 | 本次汇报里反复验证，或有两个独立证据点（两页都因此扣分 / 两篇论文都栽在这里） |
| 3.0 | 与**公开的演示设计规范**一致（能指向具体的排版/可读性准则，不是自己的单个观察） |
| 3.5–5 | **跨汇报复现过**：在 ≥2 个不同汇报项目里都成立 |

**只有严格大于 2.0 才入库**，≤ 2.0 会被服务端直接丢弃（不留文件、不进库）。
**如实自评**——为了"消掉提醒"而虚报置信度，是把库做烂的最快方式。

同指纹（`report_type + tags + kind + stage` 相同）再次入库走**强化**而非替换：
lessons 取并集、`confidence = min(5.0, max(旧,新) + 0.5)`、`confirmed_projects` 累加。
所以**换一个汇报项目又验证一次同一件事，就如实再存一次**——这让"跨汇报稳定"变成可累积的
机械事实，而不是靠自评。

## 红线（不可逾越）

| # | 红线 | 说明 |
| --- | --- | --- |
| 1 | **迁移判据：换几篇论文、换一个汇报场合之后还成立吗？** | 不成立就**不沉淀**。这是决定库质量的第一道闸——"阳虎那篇的 Figure 4 是溢出图"毫无迁移价值，收了就是噪音。**候选草稿里的大部分条目本来就该被毙掉**，这是设计意图。 |
| 2 | **不沉淀论文的研究结论与数值** | 只沉淀"怎么讲"的方法与坑。字段刻意没有 `finding` / `result_value`，防止汇报库变成二手数据源。 |
| 3 | **不沉淀受版权保护的原文长段落** | 摘录只到说明问题所需的最短片段，并标明出处页码。 |
| 4 | **负向经验必须带 `applicable_when`** | 否则不许入库（服务端会拒）。防"中文 PPT 就该少放图"这类局部假象被泛化成迷信。 |
| 5 | **经验不得进交付物** | 经验 id 只允许出现在 `00-选题/brief.md` 与 `04-评审/revision-log.md` 的「参考经验」字段，**不允许出现在 `03-产物/deck.pptx` 的页面正文、`notes.md` 讲稿或 `05-交付/汇报说明.md` 里**。经验只能改变流程与检查表，不能改变对论文的陈述。 |
| 6 | **不伪造评分** | 不允许把经验里的"上次打了 88 分"当成本次评分的依据；评分只看本次渲染产物。 |

**红线①与"仅供启发"的关系**：检索到的经验一律当作**待验证假设**，必须结合本次汇报实测确认，
**禁止直接照搬**（换一批论文它可能不成立）。

## 与文献层的分工（最容易被混淆的一条）

| | 来源 | 可否进页面 | 去向 |
| --- | --- | --- | --- |
| **论文原文** | 用户提供的 PDF | ✅ 可引用（标注页码） | `01-文献/extraction.jsonl` + `evidence.jsonl` |
| **经验层** | 自己上次汇报 | ❌ **不可进页面** | `brief.md` 的「参考经验」字段 |

像"每页正文不超过 120 字"这类**排版事实**，应该走**类型包技能**（写成硬规则并交给机械 QA 强制），
**不走经验层**。经验层存的是"我上次踩到了这个坑"，不是"这个事实为真"。

## 评分者不许读经验库

R5 的评分要**明确告诉评分者不要读经验库**——查经验库等于把生成者的先验注进评分者，
那就变成"自己给自己出题"，独立评分的成立条件被破坏。
**经验只影响生成者的流程与检查表，不影响评分者的判据。**

## 标签速查（tags 建议值）

> 标签应该描述**现象**，不是结论——这样下次检索时"我正在犯的错"能直接命中。

- **叙事**：`叙事断裂` `主线不清` `章节失衡` `结论前置` `逐篇罗列` `缺少对比`
  `对比矩阵` `共同结论` `分歧点` `缺少启发` `页数超限` `超时`
- **内容**：`复述摘要` `关键数字缺失` `图文不符` `图表错配` `断章取义` `过度解读`
  `术语未解释` `背景过长` `方法讲太细` `局限缺失`
- **视觉**：`文字溢出` `字号过小` `元素重叠` `图表过密` `配色低对比` `字体回退`
  `中英混排` `页码缺失` `公式未转图` `图片模糊`
- **评分**：`自评通胀` `扣分无依据` `无效返修` `分数不单调` `返修改坏`
- **流程**：`漏检索` `漏沉淀` `轮数超限` `未渲染即评分` `产物未落盘`
- **工具 / 技术**：`pptx 生成失败` `中文乱码` `COM 渲染失败` `字体缺失` `manifest 指纹不符`

`kind` 取值：`narrative`（叙事结构） / `content`（内容取舍与抽取） / `visual`（版式与视觉）
/ `review`（评分与返修） / `process`（流程与预算） / `pipeline`（工具链与技术）。
`stage` 取值：`R0`–`R6`（七步骨架见 `report-common` 公共段）。

## 内容组织

按照同目录 `log_template.md` 组织；`save` 时逐字段传入，memory_store 会按同样结构
生成可读 MD 日志并向量化入库。

## 半自动沉淀（R5/R6 的推荐流程）

不要靠回忆写经验——汇报流程里已经有了**结构化落盘的经验原料**，用脚本机械提取，你只负责判断。

```bash
# 1) 从汇报产物生成候选草稿（脚本只读，只回摘要，不会把整份讲稿塞进上下文）
python <BoBo根>/scripts/report_experience_candidates.py <汇报项目目录>
#    → 产出 <汇报项目目录>/04-评审/experience-candidates.md
#    想先看精简清单：加 --summary；想打印到屏幕：加 --stdout
```

提取来源与对应 `kind`：

| 来源 | 提取出什么 | kind |
| --- | --- | --- |
| `04-评审/qa-report.json` 的机械违规行 | 这类版式事故的规律（溢出/重叠/字号） | `visual` |
| `04-评审/score.json` 的**逐页扣分项** | 评分者盯的是什么、怎么扣的 | `review` |
| `04-评审/revision-log.md` 的「不改」条目 | 约束型经验（该退让的地方） | `content` |
| `04-评审/score-history.jsonl` 的轮次分数 | **分数不单调**的证据：改了 A 坏了 B | `review` |
| `00-选题/progress.md` + token 台账 | 阶段耗时、轮数、预算实耗 | `process` |

**然后你逐条做四件事**：

1. **过迁移判据**——换几篇论文、换一个汇报场合之后还成立吗？**不成立就毙掉**。
   脚本已做**预检**并把疑似项目特定的条目标成 `⚠️`（如带具体论文名、具体页码、具体分数）；
   **草稿里大部分条目本来就该被毙掉，这是设计意图，不是草稿质量差**。
2. 给留下的条目补 **`applicable_when`**（必填，服务端拒收空值）。
3. 归一化 `report_type` 与 `kind`；`tags` 优先取**上面词表**里的现象标签。
4. 如实自评 `confidence`，调 `report_experience_save` 入库——**带上 `report_project` 与 `artifacts`**，
   这样换项目复现时 `confirmed_projects` 才能机械累加。

> 脚本**不会**替你入库：是否入库、置信度多少、适用条件怎么写，全部由你判断。
> 这份草稿文件由脚本生成，**不要手写它**（改完产物重跑脚本即可覆盖）。
