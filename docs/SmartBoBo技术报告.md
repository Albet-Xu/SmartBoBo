## 一、项目定位与核心价值

### 1.1 它解决什么问题

在传统的网页取数工作中，人们通常面临两类麻烦：

- **手动复制**：打开网页、选中内容、粘贴到文档——效率低，且无法规模化。
- **程序化爬虫**：写 Python 脚本抓取——需要编程能力，且像知乎、淘宝这类网站有较强的**反爬机制**（需要真实浏览器、模拟登录、走代理等），脚本很容易失效。

SmartBoBo 的思路是：**把"采集"这个复杂任务交给一个本地 AI 智能体**。用户不需要懂爬虫、不需要懂代码，只需要在浏览器里用自然语言说一句"采集 https://xxx 这个网页"，智能体就会自动完成后续一切。

### 1.2 满足的三大需求

| 需求 | 平台的对应能力 |
| --- | --- |
| **对话式指令** | 用自然语言下达采集 / 逆向 / 入库指令，智能体自动完成意图识别与调度 |
| **真实浏览器渲染** | 采用"抗检测真实浏览器"，能执行网页 JavaScript，处理弹窗、懒加载，抓取的是渲染后的完整页面 |
| **完全本地化** | 所有处理都在本机完成，数据不出本机，不依赖任何云端采集服务 |

### 1.3 核心能力地图

平台通过"模式"概念对外提供四种业务能力，本质是同一个智能体底座搭配不同的行为设定与工具集：

- **采集模式（crawl）**：给一个网址 → 抓取并落盘到本地。
- **逆向模式（reverse）**：对一个目标网页做逆向分析（找到它背后的数据接口、加密点），并**生成一份可复用的 Python 爬虫脚本**。
- **工作流模式（workflow）**：采集网页数据 → 逐字段与用户确认 → 清洗后写入用户指定的数据库表，并沉淀为可复用的入库脚本。
- **标准模式（standard）**：通用 AI 助手，可安装 MCP 工具与技能、完成各类综合任务。

## 二、系统总体架构

SmartBoBo 采用**"前端会话 + 本地智能体编排 + 本地执行引擎"**的三层分层架构。整个系统围绕"人到指令、指令到工具、工具到执行、执行到结果"这条链路运转。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  第 1 层 · 会话与交互层（人机界面）                                           │
│  浏览器访问 http://127.0.0.1:7070 ，显示聊天界面                              │
│  · 左侧导航：会话 / 工作区 / 搜索 / ★数据库(DBX)                              │
│  · 设置区：Agent 预设切换、模型选择、技能库、MCP 工具、代理池                     │
└──────────────────────────────────────────────┬───────────────────────────┘
                                                │ HTTP / WebSocket（实时推送）
┌──────────────────────────────────────────────▼───────────────────────────┐
│  第 2 层 · 智能体编排层（dsh 运行时，DeepSeek Harness，Node.js）               │
│  · 插件化架构（Cordis）：一切能力都是可插拔的插件                                │
│  · Persona 插件    —— 把每种模式的"行为规则"注入模型提示词                       │
│  · 工具插件          —— 采集(crawl_fetch)、shell、文件系统、子代理、规划…         │
│  · MCP 客户端        —— 挂载 js-reverse（网页逆向）、dbx（数据库读）等外挂工具     │
│  · 技能库引擎        —— 扫描并加载"操作手册"型技能                                 │
└──────────────────────────────────────────────┬───────────────────────────┘
                                                │ 调用本地 Python / 读取本地数据库
                    ┌───────────────────────────┴───────────────────────────┐
                    ▼                                                       ▼
┌─────────────────────────────────────┐                 ┌───────────────────────────────┐
│  第 3 层 · 本地执行层（Python 引擎）     │                 │  DBX 数据库运行时（本地独立服务）│
│  .venv 虚拟环境，含三大采集引擎：        │  采集结果落盘     │  dbx-runtime/dbx-web.exe      │
│  · camoufox（抗检测浏览器，默认          │ ──────────────► │  Web 面板 http://127.0.0.1:4224│
│  · scrapling（轻量 HTTP）              │  当前工作区 data/ │  连接配置存 dbx-runtime/data/    │
│  · crawl4ai（AI 友好的内容提取）         │                 └───────────────────────────────┘
└─────────────────────────────────────┘
```

### 2.1 三个层次各自的职责

**① 会话与交互层**（浏览器 + dsh 前端）

用户的一切操作都发生在这里：发起对话、切换模式、下达采集指令、确认数据库字段、批准写库操作。这一层负责**把人的意图送进系统**，也把**系统的动作与结果呈现给人**。

**② 智能体编排层**（dsh 运行时）

这是整个系统的"大脑指挥部"。它解决三个问题：

- **听懂人话**：通过大语言模型解析用户意图（是不是要采集？采集哪个网址？）。
- **决定怎么做**：通过 Persona（角色规则）+ 工具集决定"采取哪些行动"。
- **调度资源**：调用采集工具插件启动 Python 引擎、调用 MCP 工具做逆向分析、调用文件系统工具读文件、调用 ask_user 工具征求用户意见。

**③ 本地执行层**（Python 引擎 + DBX 运行时）

真正"动手"干活的地方：用真实浏览器抓网页、把 HTML 转成 Markdown / 骨架、批量写库。DBX 是一个独立运行的小型数据库管理服务，用户可以在它的面板里维护好数据库连接，工作流模式的入库就复用这些连接。

> **对本层的关键设计：** 采集脚本与编排层通过"子进程调用 + 单行 JSON 结果"耦合。编排层只负责"叫脚本去干活"并接收一行结果（保存路径、状态码、摘要），**不读取文件全文**——这样职责清晰、性能好，也让 AI 不必在上下文里搬运大段网页文本。---

## 三、技术栈总览

SmartBoBo 是一个**前后端分离、跨语言栈**的项目：前端用现代 Web 技术，后端用 Node.js 生态搭建智能体框架，采集能力则用 Python 生态实现。一种更直观的理解是——**用 JavaScript 管"大脑"（AI 编排），用 Python 管"手脚"（真正抓数据）**。

### 3.1 前端（Web 界面）

| 技术 | 版本/说明 | 作用 |
| --- | --- | --- |
| React + TypeScript | — | 搭建聊天界面的组件框架，类型安全 |
| Vite / tsdown | — | 前端开发服务器与打包构建工具 |
| Zustand | — | 轻量状态管理（界面各状态） |
| CSS Modules | — | 组件级样式隔离 |
| pnpm workspace | — | 前端组件以 monorepo 方式组织（`packages/client/`） |

前端之下是 dsh 的客户端运行时，负责与后端的 WebSocket 实时通信、渲染工具调用过程、展示审批交互。

### 3.2 智能体运行时（后端核心）

| 技术 | 说明 |
| --- | --- |
| Node.js（^22 或 >=24） | 后端主运行时 |
| DeepSeek Harness（dsh） | 由 DeepSeek AI 开源的智能体框架（Agent Harness），本项目在其上做深度定制 |
| Cordis | 插件化框架，dsh 的一切能力都以插件形式挂载 |
| pnpm workspace（monorepo） | 以 `@deepseek-ai/dsh-*` 为 scope 的几十个功能分包的仓库 |
| 大语言模型（LLM） | 通过统一 provider 对接，默认配置了非常丰富的中文/国际模型（见 4.8） |

**说明：** dsh 这个 monorepo 本身非常庞大（core 核心循环、api 网关、llm 适配、session 会话、subagent 子代理、skill 技能、shell/fs、plan 计划、workflow 工作流、mcp 客户端等四十余个功能包）。本项目并没有重写它，而是**以"补丁 + 插件 + 预设"的方式在其上定制**——这正是这个架构的最大优点：骨骼是现成的、成熟稳定的，我们只需要把业务能力像插积木一样装上去。

### 3.3 采集引擎（Python）

| 引擎 | 定位 | 适用场景 |
| --- | --- | --- |
| **Camoufox**（默认） | 抗检测的真实浏览器（基于 Firefox/Playwright 内核改造），能执行 JS、应对反爬指纹检测、自动处理 Cookie 弹窗 | 绝大多数字段型网页，尤其是知乎、淘宝这类反爬强的站点 |
| **Scrapling** | 轻量级 HTTP 采集，速度快 | 结构简单、几乎无 JS 渲染的静态页面 |
| **Crawl4AI** | 对 AI 友好的内容提取，天然输出结构化 Markdown | 关注正文内容、希望直接得到干净文本的场景 |

三大引擎共享同一套"参数契约"（`--url/--out/--format/--auto-name`，结果以单行 JSON 输出），因此**可以在对话里随时切换引擎，甚至在失败时自动降级**（camoufox 失败转 scrapling，再失败转 crawl4ai）。

### 3.4 数据与存储

| 用途 | 技术 |
| --- | --- |
| Python 依赖管理 | uv（`pyproject.toml` + `uv.lock` 锁定版本，`.venv` 虚拟环境） |
| 数据库驱动 | pymysql（MySQL）、psycopg（PostgreSQL）、sqlite3（内置） |
| DBX 数据库面板 | `dbx-web.exe` 本地 Web 服务（端口 4224），连接配置存在 `dbx-runtime/data/dbx.db`（SQLite） |
| HTML 转 Markdown | html2text（主） + lxml（正文兜底抽取） |
| 网页骨架解析 | lxml（CSS 路径 ↔ 块级文本的映射） |
| HTTP 请求 | httpx（代理连通性测试等） |

### 3.5 成熟第三方体系：MCP 与 Agent Skills

这两者是当前 AI 工程领域通用的标准化扩展协议，也是本项目让智能体"长出各种能力"的关键机制：

- **MCP（Model Context Protocol，模型上下文协议）**：一套业界标准，让 LLM 可以像"接 USB 设备"一样接入外部工具。本项目通过 dsh 的 MCP 客户端挂载了 `js-reverse`（网页逆向分析）和 `dbx`（数据库只读）等 MCP 服务器。
- **Skills（技能）**：由写着 `SKILL.md` 说明文档的目录构成，相当于"教模型做某一类任务的操作手册"，模型在需要时按手册步骤执行。

> **一句话理解 MCP 与 Skills 的区别：** MCP 是给 AI "安上新的手"（可调用的工具/服务），Skills 是给 AI "递上一本说明书"（怎么做某件事）。

## 四、智能体是如何"被打造"出来的

这一章是本次报告的重点。回答一个关键问题：**一个只会聊天的通用大模型，是如何被改造成一个会采集、会逆向、会写爬虫、会往数据库入库的行业智能体的？**

### 4.1 第一步：选一个成熟稳定的"骨架"——DeepSeek Harness

我们没有从零搭建智能体框架，而是基于 **DeepSeek Harness（dsh）** 这个开源智能体框架。它提供了一整套通用能力，相当于"AI 操作系统"：

- **Agent 主循环**：模型思考 → 决定调用工具 → 得到结果 → 继续思考，循环往复直到完成任务。
- **会话管理**：多会话、历史持久化、上下文管理与自动压缩。
- **通用工具集**：执行 shell 命令、读写本地文件、子代理（把任务拆给若干"分身"）、计划模式、后台任务、定时任务等。
- **插件化架构（Cordis）**：所有能力都是插件，可加载、可卸载、可组合，配置用 YAML 声明即可。

**为什么这样做？** 因为智能体框架本身的工程量极其庞大（session、context、tool、agent-loop、delegation……），自研既慢又不稳定。站在成熟框架上定制，让我们可以把精力集中在**业务能力**（采集、逆向、入库）上。

### 4.2 第二步：用"Agent 预设"定义不同"人设"和"工具箱"

一个通用大脑如何胜任多种专业化任务？我们的答案是 **Agent 预设（preset）系统**。

每个模式都由两个 YAML 文件定义，放在 `dsh/apps/cli/config/agent-presets/<模式>/`下：

- **`preset.yml`**：界面元数据（显示名、简介、排序）。
- **`agent.cordis.yml`**：真正的"装配清单"——一行 `persona`（把行为规则注入系统提示词）+ 一张"挂哪些工具插件"的清单。

**核心思想：模式之间的差异 = "不同的行事规则（persona）" + "不同的工具集"。** 例如：

| 模式（order） | 行事规则（persona）侧重 | 挂载的核心工具 |
| --- | --- | --- |
| 标准模式 | 通用助手，可综合操作 | shell、fs、skill、web、subagent、MCP…（全量） |
| code | 编程助手 | 全量 + 代码运行能力 |
| 极简 minimal | 精简对话、低开销 | 极少量工具 |
| cordis | 插件调试 | 全量 |
| 采集模式 crawl | 检测 URL → 只采集落盘 → 汇报 | 采集工具 + shell + fs + ask-user（**极简**，无 skill/plan） |
| 逆向模式 reverse | 逆向网页接口 → 生成爬虫脚本 | 采集工具 + shell + fs + skill + plan + subagent + web |
| 工作流模式 workflow | 采集 → 逐字段确认 → 提取入库 | 采集工具 + 数据库 MCP + shell + fs + skill + plan + subagent + web |

用户在 Web 界面的 **设置 → Agent 预设** 里即可切换模式。模式切换本质上是"换了个行事规则 + 换了一套工具"，而底层大脑（模型）不变。

> **Persona 的力量来自"结构化提示词"：** 我们不是简单写一句"你是采集助手"，而是为每种模式撰写了十几页、数百行的精细规则——包括触发条件（看到 URL 就采）、授权边界（只碰用户指定的表）、交互风格（每步说明要干什么）、合规要求等。这些规则成为模型每轮决策都遵循的"宪法"。

### 4.3 第三步：让智能体"会采集"——自研工具插件 crawl_fetch

这是本项目最重要的自研代码之一：`dsh/packages/acquisition/tool-acquisition/`。

**它做了一件关键的事：把"会采集网页"这个能力，注册成一个模型可调用的工具 `crawl_fetch`。** 模型在对话中一旦判断用户要采集，就会"呼叫"这个工具。它内部完成"从用户意图到真实抓取"的中间搭桥：

```
用户说：请采集 https://zhuanlan.zhihu.com/p/xxx
   ↓ 模型识别意图，决定调用工具 crawl_fetch
tool-acquisition 插件（Node）：
   ├─ 拼接参数（url / engine / outputFormat / outFile…）
   ├─ 定位项目根的 .venv 里的 python 解释器与 scripts 脚本目录（跨机器可移植）
   ├─ 若开启了代理模式，先从代理池取一个可用代理
   └─ 以子进程方式启动：
      python scripts/run_camoufox.py --url <url> --out <data> --auto-name --format md
   ↓ Python 引擎真正抓取、转换、落盘
   ↓ 返回一行 JSON：{savedTo, status, preview, title, outputs}
   ↓ 插件解析 JSON → 回传给模型
模型向用户汇报：保存路径 + HTTP 状态 + 内容摘要（约 200 字）
```

这个设计的几个巧妙之处：

- **跨语言协作**：Node 负责"理智"（调用与解析），Python 负责"力气"（真抓）。二者通过"命令行参数进 + 单行 JSON 出"解耦，任何一个脚本失败都不影响框架。
- **可移植定位**：插件不写死任何绝对路径，而是从自身位置向上逐级查找"含 dsh 目录的根"，自动定位 `.venv`、`scripts`、`data`——**项目拷贝到任何机器都能跑**。
- **一次抓取、多格式产出**：同一份渲染后的 HTML，可同时派生 HTML 原文、Markdown、块级骨架三种文件。
- **落地到"当前工作区"**：结果默认存到用户打开对话时选定的工作区目录下的 `data/`，而不是写死在项目目录——符合用户直觉。
- **智能吸机器人性化汇报**：AI 不读取文件全文（避免天文 token 开销），只把路径、状态码、摘要回给用户。

#### 一次采集内部的"精细活"（以 camoufox 引擎为例）

`scripts/run_camoufox.py` 用真实浏览器渲染页面，其内部对"难采的页面"做了针对性处理：

1. 启动**无头（headless）真实浏览器**，导航到目标网页。
2. **自动点掉常见的 Cookie / 隐私同意弹窗**，避免正文被遮挡。
3. **等待 JS 渲染 + 滚动触发懒加载**——针对 MSN 这类"正文靠 JS 异步填充"的页面，不滚动就拿不到正文。
4. 取渲染后的完整 HTML，转成 Markdown（默认）或其它格式落盘。
5. 输出一行 JSON 供上层解析。

### 4.4 第四步：让智能体"会逆向"——MCP 工具扩展

对于反爬较强的网站，光"抓页面"不够，还需要**搞清楚这个网页的数据到底是从哪个接口来的、参数怎么加密的、cookie 怎么算的**——这就是"网页逆向"。逆向模式借助底层一套 **js-reverse MCP 服务器**（以 `npx js-reverse-mcp` 启动）向模型提供一系列逆向分析工具：

- 分析页面加载的脚本与网络请求，定位数据接口；
- 检查请求头、Cookie、签名/加密逻辑，识别密码学参数；
- 还原数据返回结构，确认要提取的字段。

逆向完成的产出，是**一份结构完整、可复用的 Python 爬虫脚本**（基于模板 `crawl_template.py` 生成），保存到工作区的 `crawl_script/` 目录。之后采集同类型网站时，工作流模式会**优先复用这些脚本**，而不必每次都用浏览器重新抓。

> 这体现了本平台"一次逆向、长期复用"的工程设计：逆向分析很贵（要调模型、要分析加密），所以把结果"固化成脚本"存下来，后续采集直接跑脚本，省钱又稳定。

### 4.5 第五步：让智能体"会入库"——数据库集成与 dbx-mcp

把采集到的数据写进数据库，是工作流模式的核心。它由三部分协作完成：

**① DBX 数据库面板（用户侧仓库）**
项目的 `dbx-runtime/` 里运行着一个独立的小型数据库管理 Web 服务（`dbx-web.exe`，端口 4224）。用户在这个面板里维护好常用的数据库连接（比如自家业务的 MySQL），连接配置持久化在 `dbx-runtime/data/dbx.db` 中。**这些连接是全平台的"数据源仓库"，工作流模式直接复用。**

**② dbx-mcp：常驻内存的数据库读接口**
为避免"每次读表结构都要临时启动一个 Python 进程"的低效，我们把数据库的**只读操作**（列出连接、读取表结构、判断表存在、执行只读 SELECT）封装成一个常驻 MCP 服务器 `dbx_mcp_server.py`，由 dsh 的 MCP 客户端以 stdio 方式拉起。它自带**连接池**和**表结构缓存**，显著加快了模型在确认阶段反复读字段的速度。暴露给模型的是 `mcp__dbx__*` 系列只读工具。

**③ 提取入库脚本（批量写库走这里）**
批量写库不经过 MCP（避免逐行数据的 JSON-RPC 序列化开销），而是让提取脚本在进程内直接连库，用 **UPSERT**（存在则更新、不存在则插入）实现去重入库。脚本骨架来自模板 `extraction_template.py`，模型只需填写中间的"定制区"（连接名、目标表、去重键、字段映射、`extract_rows()`），其余骨架不动。

> 这个"读走 MCP（快）、写走脚本进程内（省）"的设计，是数据库集成里最见功力的一处工程取舍。

### 4.6 第六步：技能库（Skills）——给模型准备的"操作手册"

模型是通用的，很多"行业内规"它并不知道。我们通过**技能库**把这些规整成可随时加载的操作手册：

- 技能存放在 `~/.dsh/skills/<名称>/SKILL.md`（或项目内 `.agents/skills/`），每个技能是一份结构化的 Markdown 说明书。
- dsh 的 `skill-filesystem` 引擎监听技能目录，模型调用技能时即可读到对应手册并照做。
- 本项目还内置了一个**"安装 MCP / 技能"的技能**（`install-mcp-and-skills`）：标准模式下，用户可以直接让 AI 从 GitHub 找到并安装新的 MCP 服务器或技能包，自动登记到设置界面，形成**可自我扩展**的能力闭环。
- 工作流、逆向模式依赖的 `db-extraction`（数据库提取入库 SOP）、`reverse-crawler`（爬虫模板）等模板技能，也是通过这一机制提供给模型的。

> 技能库是"即时发现"的，新增技能无需重启；而模式行为规则（persona）是编译进装配的，改动需重启生效。

### 4.7 代理池：智能体如何应对 IP 封锁

许多目标网站不仅检测"浏览器指纹"，还会**封锁频繁访问的 IP**。为此平台内置了一套代理池方案（`scripts/proxy_pool.py`）：

- 从第三方代理 API 批量拉取代理 IP（可配置多个来源）。
- **使用前先探测**：对目标网页发起真实请求验证代理可用——关键是"只要目标站回了任何一个 HTTP 响应（哪怕是 403）就算代理通"，因为 403 可能只是反爬挑战页，真正的裁决交给真实浏览器去处理，避免误杀可用代理。
- **状态持久化**：用过的失效代理会记入失败账本（默认 15 分钟 TTL，之后自动恢复复用），避免反复踩雷。
- **与采集流程联动**：用户通过 `/proxy` 命令开启代理模式后，`crawl_fetch` 会自动取代理 → 带代理采集 → 失败则标记该代理并换一个，最多自动重试 3 次。全部失效时**主动用 ask_user 问用户**："代理失效，是否走本地网络访问？"——绝不静默假死。
- 逆向生成的爬虫脚本同样内置了"取 IP + 轮换 + 重试 + 失效询问"的完整逻辑。

### 4.8 多模型支持：用什么"大脑"驱动

平台通过统一的大模型适配层支持极丰富的模型选择（`settings.yaml` 中配置）。当前通过一个 `opencode-go-api` provider 即可选用海量模型，覆盖国内外主流厂商：

- **国产旗舰**：DeepSeek v4（pro / flash）、Kimi（K2.x / K3）、GLM（5 / 5.1 / 5.2 / 5.3）、通义千问（Qwen3.x）、MiniMax（MiMo M2.x / M3）、讯飞（hy3）等；
- **国际模型**：GPT-5.6、Grok 4.5 等。

模型可在 **设置 → 模型** 里随时切换。不同任务可以选择不同"大脑"（例如普通采集用性价比高的模型，写复杂爬虫用代码能力强的模型）。`agent-default-model` 还提供了默认模型设置，界面也支持直接配置 API Key。

## 五、核心工作流程详解

### 5.1 采集模式：一次采集的完整生命周期

以"请采集 https://zhuanlan.zhihu.com/p/xxx"为例，系统内部经历：

```
① 意图识别（模型 + persona）
   输入含 http(s):// → 判定为采集意图；多个 URL → 逐个采集后汇总；
   用户说"不采集/仅讨论网站" → 不触发。
        ↓
② 引擎选择
   默认 camoufox；用户可说"用 scrapling 采"切换。
        ↓
③ 工具调用（tool-acquisition，Node 编排）
   组装 python 子进程命令 → 启动引擎脚本。
        ↓
④ Python 引擎抓取（执行层）
   真实浏览器导航 → 关 Cookie 弹窗 → 等 JS 渲染 + 滚动触发懒加载
   → 取渲染后 HTML → 转 Markdown / HTML / 骨架 → 落盘到工作区 data/
   → stdout 输出单行 JSON。
        ↓
⑤ 汇报
   模型向用户汇报：保存路径 + HTTP 状态码 + 内容摘要（前 200 字）。
```

交付示例：

```
采集完成：
- 已保存: data/zhuanlan_zhihu_com_标题_20260820-154238.md
- HTTP状态: 200
- 预览: …（正文开头约 200 字）
```

### 5.2 逆向模式：从网页到可复用爬虫脚本

逆向模式的目标不是"存一页"，而是"产出一个能长期、稳定采同类型页面的爬虫程序"。

```
用户：逆向分析 https://example.com，生成爬虫
   ↓
① 判断触发：识别"逆向/破解/爬取/反爬/数据接口"等关键词 + 网址
   ↓
② 逆向分析：用 js-reverse 等 MCP 工具
   · 定位数据接口、分析 URL 参数 / 请求头 / Cookie / 签名 / 加密逻辑
   · 识别 JS 中对参数的加密、混淆、时间戳签名等难点
   · 确认返回结构（JSON/HTML）与目标字段
   ↓
③ 遇难点主动 ask_user：不猜测、不编造，问用户要关键信息（token、构造方法等）
   ↓
④ 复用 reverse-crawler 模板技能，生成结构完整、可复用、带注释的 Python 脚本
   · 若开启代理模式，脚本内嵌"代理池取 IP + 轮换 + 重试 + 失效询问"逻辑
   ↓
⑤ 保存到工作区 crawl_script/<脚本名>.py，并汇报脚本路径、运行方式、依赖、逆向结论
```

**沉淀成果：** `crawl_script/` 目录相当于平台的"逆向资产库"，后续工作流模式的批量采集会优先调用这些脚本。

### 5.3 工作流模式：采集 → 确认 → 入库（六阶段 SOP）

工作流模式是平台最复杂、也最能体现"人在回路"（Human-in-the-loop）设计的能力。它的目标是把网页数据写进用户指定的数据库表，且**每个字段都经过用户确认**，绝不猜测入库。整个流程被 format 为一套严格的六阶段 SOP：

**阶段一：读取数据库字段（只针对被授权目标表）**

1. 定位 BoBo 根目录（含 `dbx-runtime` 的目录）。
2. 用 `mcp__dbx__list_connections` 复用 DBX 已保存连接；没有则询问用户或引导新建。
3. 用 `table_exists` / `describe_table` 校验目标表存在并读取其全部字段（名称、类型、主键、可空）。
4. **授权边界（强制）**：只操作目标表；参考表仅只读 describe。空白新表 → 询问建表 SQL 或逐个定义字段。

**阶段二：严格逐一确认字段含义**
- 拿到全部字段后，**逐个**用 ask_user 询问含义与数据来源，问完一个再问下一个，不跳过、不默认通过。
- 每个字段可给出**推荐方案**（如 NOT NULL 的配置类字段推荐默认值 `fetcher='http'`、`enabled=1`、`created_at=NOW()`），但推荐不能代替询问。

**阶段三：抓样品页了解结构**
- 优先复用 `crawl_script/` 里已有的逆向脚本，否则用 crawl_fetch 抓一个样品页。
- 枚举页面能提供的信息点（标题、正文、价格、日期等）与样例值；同类型网址只需一个样品。

**阶段四：核对字段满足度 & 补空值/固定值**
- 逐字段对照样品：能提取的标记来源；页面满足不了的**逐个询问**填 NULL 还是用户给的固定值。
- 整理最终字段映射，**再与用户确认一次**后才进入写脚本。

**阶段五：写提取入库脚本（复用模板省 token）**
- 先看工作区 `extraction_scripts/index.md` 是否已有"同类型网址→同目标表"的脚本，有则直接复用。
- 否则复制 `extraction_template.py` 生成新脚本，**只填写 `# ⛏️ GEN-CUSTOM` 定制区**（连接名、目标表、去重键、固定值、`extract_rows()`），通用骨架（连库、UPSERT、预览、CLI）全部来自模板。

**阶段六：批量采集与入库（采集/入库分离，UPSERT 去重）**
1. **批量来源**：一批 URL / 一个网址清单文件 / 已抓好的 `data/` 目录。
2. **采集**：对每个网址优先跑匹配的逆向脚本，否则 crawl_fetch **按引擎降级**（camoufox → scrapling → crawl4ai），且输出格式与提取脚本期望一致。
3. **入库**：`python 脚本 --data data`（脚本遍历文件提取并写库）。
4. **预览再写库**：先 `--dry-run` 展示待写入行 → 用户确认 → 正式运行 → **只写目标表**，按主键/唯一键 UPSERT（存在更新、不存在插入，实现无重复入库）。
5. **汇报**：插入/更新条数、目标表、脚本路径。

> **设计精髓："采集与入库分离"** —— 昂贵的采集（浏览器抓取）和便宜的入库（脚本写库）解耦。同一批数据可以先采下来存为文件，再在一个脚本里批量入库，便于预览、复查和重跑。

## 六、安全、合规与数据隐私设计

作为一个会"联网、写文件、写数据库"的智能体，安全性是重中之重。平台在多个层面做了约束：

### 6.1 数据隐私
- **完全本地运行**：采集、转换、入库全部在本机完成，网页数据不经过任何云端采集服务。
- **API Key 妥善管理**：大模型密钥存在 `dsh/.env`，已被 `.gitignore` 排除，**不会进版本库**；Web 界面的密钥配置同样走本地存储。

### 6.2 操作授权边界
- **数据库写库仅限目标表**：强制只操作用户明确给出的目标表；参考表只读、绝不写入。
- **写库前必须 dry-run 预览并获确认**：有副作用的操作（写库）绝不静默执行。
- **字段逐一个别确认**：推荐方案不能代替询问，杜绝"一次性批量默认通过"。

### 6.3 过程透明
- 执行 shell / 采集命令前，模型会先说明"我将运行以下命令：…"，让用户看到每一步。
- 任何工具调用失败都不会静默结束回合，而是把错误原文 + 可执行的下一步建议反馈给用户。

### 6.4 合规提醒
- Persona 中内置合规约束：尊重目标网站服务条款与反爬规则，不用于绕过付费墙或损害他人权益；对采集频率、范围与写入目的保持合理与合规。

## 七、工程化与可移植性设计

### 7.1 环境管理（锁版本、可复现）

| 侧 | 工具 | 说明 |
| --- | --- | --- |
| Node 侧 | pnpm + `pnpm-lock.yaml` | 一次性安装 dsh 全部依赖 |
| Python 侧 | uv + `pyproject.toml` + `uv.lock` | `uv sync` 一键按锁定版本复现 `.venv`；`.python-version` 固定 3.13 |
| 浏览器内核 | `camoufox fetch` | 首次拉取抗检测浏览器内核 |

依赖版本全部锁定在锁文件里，**换机器可以完整复现**，这是工程化的重要保障。

### 7.2 一键启动
`启动.cmd`（Windows）/ `启动.sh`（Linux/macOS）完成两件事：

1. 自动把 `BOBO_ROOT` 指向本项目根目录（采集插件据此定位 `.venv` 与 `scripts`，无需手改路径）。
2. 先拉起 DBX 数据库服务（独立窗口，端口 4224），再启动 dsh Web 服务（`pnpm bobo`，端口 7070）。

### 7.3 可移植性（跨机器、跨平台）
- 采集工具插件**不写死任何绝对路径**，用"向上查找含 dsh 目录的根"自动定位项目资源。
- cordis 装配补丁使用裸包名（`@deepseek-ai/dsh-tool-acquisition`），由 dsh 自动 link，任意机器都能解析。
- 脚本路径使用平台差异处理（Windows 用 `.venv/Scripts/python.exe`，其余用 `.venv/bin/python`）；输出编码强制 UTF-8，规避 Windows GBK 乱码。

### 7.4 主要目录速览

```
SmartBoBo/
├── dsh/                          # DeepSeek Harness（Node pnpm monorepo，智能体运行时）
│   ├── apps/cli/config/agent-presets/  # ★ 各模式预设（persona + 工具集）
│   ├── packages/acquisition/tool-acquisition/  # ★ crawl_fetch 采集工具插件
│   ├── packages/client/          # Web 前端（含数据库入口、品牌）
│   └── patch/                    # 装配补丁（注入采集插件、固定端口 7070）
├── scripts/                      # ★ Python 采集脚本（三引擎 + 共享模块 + 代理池 + dbx-mcp）
├── engines/                      # 采集引擎源码（scrapling / crawl4ai）
├── dbx-runtime/                  # ★ DBX 数据库运行时（dbx-web.exe + data/dbx.db）
├── .venv/                        # Python 虚拟环境（uv 管理）
├── pyproject.toml / uv.lock / .python-version   # Python 环境与依赖锁定
├── 启动.cmd / 启动.sh             # 一键启动
└── docs/                         # 说明文档
```

## 八、数据输出与格式体系

采集引擎能产出三种互补的格式，满足不同下游需求：

| 格式 | 扩展名 | 内容 | 典型用途 |
| --- | --- | --- | --- |
| **Markdown** | `.md` | 网页正文的干净文本（默认格式） | 阅读、归档、一般正文入库 |

文件名自动生成为 `站点域名_页面标题_时间戳.<扩展名>`，存储在**当前会话工作区**的 `data/` 目录（无则自动创建），用户可按需归档。
