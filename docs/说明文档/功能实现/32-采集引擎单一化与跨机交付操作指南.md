> 适用范围：BoBo 桌面版 v1.3.5+（`bobo-application-02` 分支持续演进）。

> ① 采集引擎单一化（camoufox only）与包体瘦身；
> ② 逆向↔工作流模式切换修复与「逆向升级链路」；

## 一、采集引擎单一化（camoufox only）与包体瘦身

### 目标
- 打包产物只保留 **1 个 camoufox 内核最新版**（当前 `152.0.4-beta.29`），删除历史旧版；
- 所有浏览器功能（采集、搜索、渲染）**只能调用 camoufox**；scrapling / crawl4ai 及其依赖整体移除；
- 安装包体量从 ~1.5GB 降到 ~0.6-0.7GB。

### 已做的改动（代码层）
| 位置 | 改动 |
|---|---|
| `pyproject.toml` | 删除 `scrapling[fetchers]` / `crawl4ai` 依赖与 `[tool.uv.sources]` 本地路径源；保留 `camoufox>=0.5.5` 与 `override-dependencies: playwright<1.61`（camoufox 协议约束） |
| `.venv` | `uv sync` 重装：venv 从 695MB 降到 355MB；`playwright`（108MB）为 camoufox 运行依赖，**必须保留，不可删** |
| `engines/` | 整库删除 scrapling、crawl4ai 源码（git 历史可恢复） |
| `scripts/` | 删除 `run_scrapling.py` / `run_crawl4ai.py`；保留 `run_camoufox.py`、`browser_server.py`、`crawl_common.py` |
| `tool-acquisition`（crawl_fetch） | 移除 `engine` 参数；统一调用 `run_camoufox.py`；失败只「重启长驻浏览器服务」重试一次 |
| agent-presets（crawl / workflow） | 提示词改为单引擎口径，删除"三引擎降级"描述 |

### 操作：如何维护/复现
```bash
# 1) 依赖环境（引擎变更后执行，自动删多余包）
uv sync

# 2) 冒烟验证（浏览器服务 + 采集链路）
python .venv/Scripts/python.exe scripts/browser_server.py --profile-dir /tmp/p  &
# 等日志出现 READY <端口> 后：
python .venv/Scripts/python.exe scripts/run_camoufox.py \
  --url https://example.com --out /tmp/o --server 127.0.0.1:<端口> --format md
# 预期 stdout 一行 JSON：status 200 / title / savedTo
```

### 操作：打包时 camoufox 内核只保留新版
打包清单（`desktop/package.json` → extraResources）已对 camoufox 源缓存加过滤：
```json
{ "from": "C:/Users/ausu/AppData/Local/camoufox", "to": "runtime/camoufox",
  "filter": [ "**/*", "!**/browsers/official/152.0.4-beta.28-*/**" ] }
```
- 该清单只入 **beta.29**（`config.json` 的 `active_version` 指向它）；
- 本机缓存里的旧版 `~/AppData/Local/camoufox/camoufox/Cache/browsers/official/152.0.4-beta.28-*` 可手工删除（省 ~936MB 磁盘），删除不影响新版；
- **camoufox 升级后**（pyproject 升版本 → `uv sync` → 启动一次应用触发内核下载）：确认新版本目录名，并同步更新上面 filter 的排除项。

## 二、逆向↔工作流模式切换修复 + 逆向升级链路

### 背景与根因
- 两个模式此前**都挂载同名的 `mcp-reverse-memory`**（同名 serverName → 工具 `mcp__reverse-memory__*`）；
- dsh 的 MCP 桥在工具**注册冲突时以 contain 策略静默回滚**，导致"逆向→工作流"切换后新模式的一只 MCP 工具集体丢失，表现为切换不成功。

### 已做的改动
- `workflow/agent.cordis.yml`：只读实例改用独立 `serverName: reverse-memory-ro`（工具 `mcp__reverse-memory-ro__*`，提示词同步），与逆向模式的读写实例彻底隔离，任何顺序挂载都不冲突；
- 逆向模式保持 `reverse-memory`（读写）不变。

### 逆向升级链路（工作流 → 逆向的自动接力）
`workflow/agent.cordis.yml` 新增固定规则：
1. 采集只走 `crawl_fetch`（camoufox 唯一引擎），失败时工具自动重启浏览器服务重试一次；
2. **重试后仍失败**且特征命中反爬（412/403/验证码/JS 混淆 SDK/动态 cookie/登录态）→ 停止自行换方案；
3. 请用户在界面**切换到逆向模式**并附交接信息（URL、已尝试与报错、反爬特征、失败样本路径）；
4. 逆向模式接手解析并沉淀经验；解决后切回工作流继续批量采集。
> 注：当前切换需用户在界面操作（会话预设切换）；若后续需要「模型自动切换」，需改造 dsh 会话预设事件机制，另行设计。

## 三、失败案例置信度沉淀规则（服务端已实现）

`memory_store.save_experience()` 已按以下规则执行：
- 置信度 **≥ 1.8**：写本地 MD 日志 + 向量化入 Qdrant（成功/失败案例**都**按此评估）；
- 置信度 **< 1.8**：直接丢弃，**不写任何文件**；
- 只读模式（工作流）调用写工具直接拒绝。

提示词已同步（reverse 预设第 2 条、workflow 升级链路），模型会为成功/失败案例都按 1.8 门槛评估沉淀。

## 四、DBX 离线驱动与 Qdrant 连接（手工配置）

### 随包离线驱动包
- 安装包已附带官方 JDBC 驱动插件：安装后位于 `<安装目录>\resources\runtime\dbx-offline\dbx-jdbc-plugin-0.1.37.zip`；
- 用途：DBX 连接 Kafka / Qdrant / OceanBase 等需要驱动下载的库时，先用它或在「驱动管理」里导入/离线安装；默认仓库不通（Maven Central 被墙）时也可在驱动下载对话框改选**阿里云 / 华为云 / 腾讯云镜像**。

### 连接公司服务器上的 Qdrant（手工步骤，供所有同事照做）
**推荐：在 DBX 面板建连接（RAG 自动复用）**
1. 打开 BoBo → 左侧「数据库」面板；
2. 新建连接：类型选 **Qdrant**；
3. 填写：主机 = 公司 Qdrant 服务器地址（如 `192.168.x.x` 或内网域名）、端口 = `6333`（默认）、API Key（如公司要求）、连接名称自定；
4. 保存并测试连接成功；
5. RAG 记忆库（`memory_store`）会自动找到 `db_type == qdrant` 的连接作为向量库，无需其他配置；
6. 验证：让助手调用 `mcp__reverse-memory-ro__stats`（工作流）或 `reverse_memory_stats`（逆向），看到 `qdrant_reachable: true`、集合名 `reverse_experience` 即成功。

**备用：环境变量直指（不经 DBX 连接）**
- 在应用启动环境设置：`REVERSE_MEMORY_QDRANT_URL=http://公司服务器:6333`、`REVERSE_MEMORY_QDRANT_API_KEY=xxx`（优先级高于 DBX 连接）；
- 集合名固定 `reverse_experience`，首次写入自动建集合；如公司 Qdrant 禁止自动建集合，可先在服务端手工创建同名空集合；
- API Key 只存于 DBX 连接/环境变量，不进经验正文与日志。

## 五、跨机打包与发布流程（含瘦身后的验证闭环）

### 打包前置（每次发版）
```bash
# 1) Python 环境就绪（单引擎）
uv sync

# 2) 同步 dsh 源码进 staging（排除依赖/构建产物）
robocopy E:\SmartBoBo\dsh E:\SmartBoBo\desktop\staging\dsh /MIR \
  /XD node_modules .git __pycache__ /XF *.log *.tsbuildinfo

# 3) 核对打包输入
#    - staging/dsh/pnpm-store：v11/files + index.db（剔除 projects/、links/ 目录联接）
#    - staging/pnpm-cache：与 lockfile 匹配的完整元数据（缺包会离线重建失败）
#    - staging/dbx-offline/*.zip：官方 JDBC 驱动插件在
```

### 打包与首启验证
```bash
cd desktop
ELECTRON_BUILDER_CACHE="E:\Develop Tools\Electron" \
ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/" \
ELECTRON_BUILDER_BINARIES_MIRROR="https://npmmirror.com/mirrors/electron-builder-binaries/" \
npm run dist -- --config.directories.output=release-<版本>

# 首启验证（真机模拟"干净机器"）：
#   ./release-<版本>/win-unpacked/BoBo.exe  （注意环境变量 ELECTRON_RUN_AS_NODE 不能为 1）
#   → 观察 ../BoBoData/electron/bobo-pnpm.log：resolved/reused/downloaded 0、“Done in ~15s”、无 GET https 警告
#   → 127.0.0.1:7070 返回 200；BoBoData/dsh/skills 已被播种；runtime/.venv/pyvenv.cfg 指向 runtime/python
```

### 发布（Gitea Release + 分卷上传）
- 服务器对单次上传约 10-12 分钟超时、链路约 1MB/s，>600MB 的单文件请**分卷**（每卷 ≤500MB）；
- 流程：建 v1.3.x Release（`target_commitish=bobo-application-02`）→ 依次上传分卷 + `.sha256` + 合并说明；
- 合并命令（收件人）：`copy /b BoBo-Setup-1.3.5.exe.aa + ...ab + ...ac BoBo-Setup-1.3.5.exe`，SHA256 校验后安装。

### 包内瘦身自检清单
- `resources/runtime/camoufox/camoufox/Cache/browsers/official/` 只有 1 个版本目录；
- `resources/runtime/scripts/` 无 run_scrapling / run_crawl4ai；
- `resources/runtime/` 无 `engines` 目录；
- `.venv/Lib/site-packages` 无 scrapling / crawl4ai / fake_useragent（playwright 保留）。
